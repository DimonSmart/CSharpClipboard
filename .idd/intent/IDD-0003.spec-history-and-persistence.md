# IDD-0003.spec-history-and-persistence

## Intent

Надёжно сохранять историю с поиском, pins и retention.

## Related Specifications

- IDD-0002
- IDD-0004
- IDD-0011

## Behavior

- По умолчанию максимум **500** уникальных незакреплённых текстов; настройка **50–2000**. Закреплённые записи не входят в лимит и не удаляются автоматически.
- **Точное совпадение UTF-8** означает одну запись (включая возможные `\0`, LF, пробелы, регистр). SHA-256 — только индекс кандидата, окончательная проверка сравнивает весь BLOB.
- Повторное копирование обновляет `copiedAt`, известный `source` и положение среди Recent; не меняет первоначальный `createdAt` и не снимает pin.
- Несовпадающие только регистром, пробелами, концом строки или Unicode normalization тексты считаются **разными**.
- После insert, повторного copy или unpin детерминированно удалить oldest unpinned сверх лимита.
- Pin/unpin любой записи. Pinned вверху по `pinnedAt DESC`, затем Recent по `copiedAt DESC`; stable tie breaker ID. Unpin возвращает в Recent и сразу применяет лимит.
- Отдельные команды Delete, Clear Recent (сохраняет все pins), Clear All (с явным подтверждением, удаляет всё).
- Поиск включает pins и Recent, Unicode-aware case-insensitive substring matching в русском, английском и тексте с акцентами; не менять сортировку ради поискового результата. **Отдельно проверить** соответствие .NET по отношению к Swift Foundation, не утверждать идентичность без тестов.
- При открытой History первоначальный порядок записей **заморожен**: pin/recopy не переставляют существующие строки. Панель показывает снимок на момент открытия без фонового обновления; новые копирования видны только при следующем открытии. Явные команды pin/unpin, Delete и очистки отражаются в списке без добавления новых записей. Поиск фильтрует текущую коллекцию с сохранением этого порядка. После закрытия/повторного открытия сортировка пересчитывается.
- Длинный текст усекать **только в preview**, БД хранит точное значение.
- База и preferences сохраняются при рестарте. Отсутствие разрешения capture не препятствует чтению истории.

## Product-Significant Architecture And Constraints

- SQLite, schema version **1** совместима по полям с референсом (см. приложение ниже): `id TEXT PRIMARY KEY`, `content BLOB`, `digest BLOB`, `created REAL`, `copied REAL`, `source TEXT NULL`, `pinned REAL NULL`.
- `digest = SHA-256(raw UTF-8)`; `created/copied/pinned` — Unix seconds (дробная часть допустима). `id` — canonical UUID/GUID text; нормализовать регистр при чтении и сравнениях.
- Мутации истории атомарны.
- Версионированные миграции через `PRAGMA user_version`; более новая неизвестная версия приводит к понятной ошибке, **не** к молчаливому удалению или downgrade.
- Обслуживание БД не блокирует UI; после повторных циклов заполнения и очистки размер не растёт неограниченно.
- Непустая БД после crash остаётся логически непротиворечивой;
- История хранится в приватном app-specific каталоге пользователя, вне iCloud/OneDrive-каталогов по умолчанию: ориентир macOS `~/Library/Application Support/CSharpClipboard/history.sqlite`, Windows `%LOCALAPPDATA%\CSharpClipboard\history.sqlite` (реальные пути получать через OS APIs, не конкатенировать по строковому шаблону). macOS права 0700 на директорию, 0600 на БД по возможности; Windows ACL для текущего пользователя. Отмечать, что ОС и резервное копирование контролируются пользователем.
- Новое приложение не должно автоматически подключаться к старому `ClipboardMac/history.sqlite` и менять его; миграция старой истории — отдельная будущая функция.

## Non-goals

Нет автоматического подключения старой БД ClipboardMac; preview не изменяет данные.

## Acceptance Criteria

- Циклы заполнения 2000 → очистка → повторное заполнение не приводят к неограниченному росту файла после maintenance.
- Exact Unicode corpus с emoji, CRLF, NUL, combining marks, trailing spaces — все различные ожидаемые варианты сохранены.
- Pin переживает retention, Clear Recent и restart.
- Нет потери atomicity при исключении во время транзакции.
- 500 элементов + разумное число pins фильтруются без ощутимых задержек; начальная проверка: 100 поисков в контрольном наборе менее ~2 секунд на тестовой машине (фиксировать аппаратные условия, не выдавать этот порог за универсальную гарантию).

## Verification

Реальный SQLite на обеих ОС: точный Unicode corpus, коллизии digest с полным сравнением, rollback/busy, миграции/неизвестная версия, restart, pins/retention и fill/clear/maintenance. Замеры поиска сопровождаются данными оборудования.
